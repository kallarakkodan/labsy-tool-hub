# 18 — lib/auth.ts: scrypt verification, sealed session cookie, gen:hash

Status: resolved
Phase: P2
Blocked by: 03
Spec: PRD §8.1, CONTEXT §4, CONTEXT §7.4 (isAdmin), CONTEXT §8 step 6

## Why

`isAdmin` feeds `toolVisibilityWhere` on every read path. Until this lands, the
visibility system is only half-tested.

## Scope

One module, `src/lib/auth.ts`, per
[ADR-0001](../../../docs/adr/0001-session-format-jose-jwe.md) and PRD §10. The
Next 16 route guard (`proxy.ts`) runs on the **Node.js** runtime, so there is no
Edge boundary to split around:

- `verifyPassword(plain)` — scrypt against `ADMIN_PASSWORD_HASH`, compared with
  `crypto.timingSafeEqual`
- `seal()` / `unseal()` — compact JWE via `jose`, `alg: "dir"`, `enc: "A256GCM"`,
  key derived from `AUTH_SECRET` by HKDF-SHA256, `SESSION_TTL_HOURS` expiry
- `getSession()` — returns the session or `null`
- `isAdmin()` — `getSession() !== null`
- Cookie: `labsy_session`, HttpOnly, `SameSite=Lax`, `Secure` from
  `COOKIE_SECURE`, `Path=/`.
- `scripts/gen-hash.ts` + `pnpm gen:hash` — prompts for a password (no echo),
  prints the `ADMIN_PASSWORD_HASH` line to paste into the env file.
- Replace the `isAdmin` stub in issue 11's routes with the real call.

## Done when

- [x] Tests: correct password verifies; wrong password fails; a hash generated by
      `gen:hash` round-trips
- [x] Test: a cookie with a tampered payload or signature is rejected
- [x] Test: an expired session is rejected
- [x] Test: an admin session now sees drafts and internal tools through
      `/api/tools` (the case stubbed in issue 11)

## Watch out

- Timing-safe comparison on the **derived key**, not on the password string.
- `getSession()` must never derive admin-ness from a query param, header, or
  anything else client-controlled (CONTEXT §7.4).
- Sessions are stateless — no revocation. Logout clears the cookie; rotating
  `AUTH_SECRET` is the break-glass. Recorded and accepted in ADR-0001.
- `cookies()` is async in Next 16 — `await cookies()` in both seal and unseal.
- Store the scrypt parameters (N, r, p, salt) in the hash string so they can be
  raised later without invalidating the format.

## Answer

`lib/auth.ts` is real, `pnpm gen:hash` works, and — the part that mattered — the
whole visibility system was verified end to end with an actual sealed cookie
rather than a mock:

```
anonymous            total: 4  categories: Dev Tools, OS Images, Utilities
sealed session       total: 6  categories: Dev Tools, Drivers, OS Images, Utilities
                       intel-network-driver-bundle -> INTERNAL
                       windows-11-dev-kit          -> DRAFT
/api/tools/windows-11-dev-kit           404 anonymous  ->  200 with session
/api/tools/intel-network-driver-bundle  404 anonymous  ->  200 with session
forged cookie                           404 (treated as anonymous)
```

The **Draft** and **Internal** badges from issue 15 had never rendered against a
live session — only against mocked tests. They have now, in a browser, and the
"Drivers" pill appears alongside them.

Decisions:

- **scrypt parameters live inside the hash string** (`scrypt$N$r$p$salt$hash`),
  so they can be raised later without a format migration or invalidating
  existing hashes. `N=16384, r=8` needs ~16 MiB, under Node's default 32 MiB
  `maxmem`; going past 2^15 requires passing `maxmem` explicitly, which is noted
  in the code because it fails confusingly otherwise.
- **The key is HKDF-derived from `AUTH_SECRET`,** not the secret used directly.
  A fixed info string means the same secret could later key a second purpose —
  a signed download URL, say — without the two sharing key material.
- **`unsealToken` returns null for every failure mode**: tampered, truncated,
  expired, or sealed under a different secret. Callers must not distinguish
  them; they are all just "not signed in".
- **`promisify(scrypt)` types away the options overload.** A hand-written
  wrapper keeps N/r/p passable — `promisify` compiled but would not typecheck
  with the parameters this needs.

Two dev helpers landed in `scripts/`: `dev-hash.mts` (non-interactive hashing)
and `dev-token.mts` (seal a session). Both require the real `AUTH_SECRET` from
`.env.local`, so they grant nothing an operator does not already have, and they
are what let this issue be verified before the login route exists. `dev-token`
becomes redundant once issue 20 lands.

`pnpm gen:hash` prompts twice with echo suppressed and never accepts the
password as an argument — argv would put it in the shell history of whoever ran
it. It warns below 12 characters, since this is the only credential protecting
the admin panel and it is shared (PRD §11.4).
